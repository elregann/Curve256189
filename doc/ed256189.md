# Ed256189

**Status:** implemented in `1.0.0-beta.5`; experimental, not independently
audited.

Ed256189 is an EdDSA instance for Curve256189 built on the complete twisted
Edwards model `E_{d,a}`. It follows the EdDSA algorithm of
[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) wherever the curve permits
it. This document records the parameter set, the exact byte formats, the
signing and verification rules, and every place where Ed256189 deliberately
differs from RFC 8032.

Ed256189 is the intended replacement for the earlier `XEdDSA` scheme. `XEdDSA`
is kept for backwards compatibility and is documented as superseded; it is not
changed by this release. The two schemes are **not** wire-compatible with each
other and produce unrelated public keys from the same seed.

---

## 1. Summary

| Property | Value |
|---|---|
| Signature curve | `E_{d,a}: d·u² + v² = 1 + a·u²·v²` |
| Field | `p = 2²⁵⁶ − 189` |
| Hash | SHA-512 |
| Seed / private key | 32 bytes |
| Public key | 33 bytes (`v` little-endian, then parity of `u`) |
| Signature | 65 bytes (`R` 33 bytes, then `S` 32 bytes little-endian) |
| Cofactor | 4 |
| Subgroup order | 254-bit prime `n` (called `ℓ` in this document) |
| Nonce | deterministic, domain-separated, retry counter |
| Verification | strict, non-cofactored, prime-order subgroup checks |
| Variants | PureEdDSA only; no context and no prehash in v1 |

Ed256189 is **not** compatible with Ed25519, Ed448, Ed25519ctx, Ed25519ph, or
XEdDSA. It has its own domain separator and its own key format.

## 2. Parameters

### 2.1 Field

```
p = 2^256 − 189
  = 115792089237316195423570985008687907853269984665640564039457584007913129639747
  = 0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff43
```

`p` is prime, `p ≡ 3 (mod 4)` and `p ≡ 3 (mod 8)`. Because `p ≡ 3 (mod 4)`, a
square root of a quadratic residue `x` is `x^((p+1)/4) mod p`.

The field is a full 256-bit prime (`p > 2^255`), so a field element needs all
32 bytes. There is no spare high bit available for a sign bit; see
[§7](#7-wire-format) and [§11](#11-deviations-from-rfc-8032).

### 2.2 The two Edwards models

Curve256189 is birationally equivalent to two twisted Edwards curves:

| Model | Equation | Coefficient of `x²` | Coefficient of `x²y²` |
|---|---|---|---|
| Natural `E_{a,d}` | `a·x² + y² = 1 + d·x²y²` | `a = A + 2 = 479599` (non-square) | `d = A − 2 = 479595` (square) |
| Dual `E_{d,a}` | `d·u² + v² = 1 + a·u²v²` | `a' = d = 479595` (square) | `d' = a = 479599` (non-square) |

RFC 8032 (§3, parameters 7 and 8) requires the coefficient `a` to be a non-zero
square and the coefficient `d` to be a non-square. The natural model of
Curve256189 has these the other way round, so the signature curve is the
isomorphic dual model `E_{d,a}`. On `E_{d,a}` the standard twisted Edwards
addition law is complete: both denominators are non-zero for every pair of
points on the curve.

The isomorphism is the involution

```
Phi(x, y) = (−x, 1/y) : E_{a,d} → E_{d,a},
Phi(P + Q) = Phi(P) + Phi(Q),   Phi(Phi(P)) = P.
```

All Ed256189 arithmetic is performed on `E_{d,a}` with `DualEdwards`. In this
document, `(u, v)` are the coordinates on `E_{d,a}`.

### 2.3 Group structure

```
#E = 4 · n,   n = 28948022309329048855892746252171976963257918617752773869725216245594308445583
```

`n` is prime and has 254 bits. The cofactor is `h = 4 = 2^2`, so `c = 2` in the
notation of RFC 8032. The group `E` is isomorphic to `Z/4Z × Z/nZ`: it has the
identity, one point of order 2, two points of order 4, and the prime-order
subgroup of order `n`.

In this document the subgroup order is written `ℓ`, to avoid a collision with
the RFC 8032 parameter `n` (which is the bit position of the top bit of the
secret scalar, `n = 254` for Ed256189). The library calls the subgroup order
`Curve256189Params.n`.

### 2.4 Generator

The Montgomery base point is

```
Gx = 107794463287790729181798923754704247240057009056848862892287801730172665808003
Gy = 5935226473593038842940459288042955305454636525326183552707973708623513097342
```

The **signature generator** is its image under `Phi`:

```
B = Phi(G) = (−x_G / y_G, (x_G + 1) / (x_G − 1))
  = (27540090778475722458859912069786520005272669495736742504068642751571152792437,
     61352474183582518690701076899155636884634044451932967862134646816316862676782)
```

Encoded as 32-byte little-endian `v` followed by parity:

```
B = 87a44512042fd91369d0005f710e89a7c6fbd4cb789c555f1a0962af259ebf2e00
```

`B` is not the identity and `[ℓ]B` is the identity, so `B` generates the
prime-order subgroup. These facts are checked by the test suite and by the
independent Python reference.

Known low-order encodings:

| Point | `(u, v)` | 33-byte encoding |
|---|---|---|
| Identity | `(0, 1)` | `01` followed by 31 zero bytes, then `00` |
| Order 2 | `(0, −1)` | `42` followed by 31 `ff` bytes, then `00` |
| Order 4 (even `u`) | `(98003860010952499363772820613200450438822562101502438443250426135397978578906, 0)` | 32 zero bytes, then `00` |
| Order 4 (odd `u`) | `(17788229226363696059798164395487457414447422564138125596207157872515151060841, 0)` | 32 zero bytes, then `01` |

The two order-4 points have `v = 0` and `u = ±sqrt(1/a')`.

## 3. Notation and primitives

* `LE(x, k)` is the `k`-byte little-endian encoding of a non-negative integer
  `x`, least significant byte first.
* `LE⁻¹(bytes)` is the inverse operation.
* `‖` is byte-string concatenation.
* `SHA-512(x)` is the 64-byte SHA-512 digest of `x`.
* `mod ℓ` is reduction to the canonical representative in `[0, ℓ)`.
* `[k]P` is scalar multiplication of the point `P` by the integer `k`.
* `enc(P)` is the 33-byte point encoding of [§3.1](#31-point-encoding).
* `dec(bytes)` is the point decoding of [§3.2](#32-point-decoding).

### 3.1 Point encoding

For a point `P = (u, v)` on `E_{d,a}`:

```
enc(P) = LE(v, 32) ‖ OCTET(u mod 2)
```

The final byte is the parity of `u`: `0` if `u` is even, `1` if `u` is odd.
`v` must already be reduced modulo `p` (the library always produces canonical
coordinates).

This is the direct analogue of RFC 8032's "encode `y`, then copy the least
significant bit of `x`" rule, with the sign kept in a separate byte because
`p` is 256 bits wide.

### 3.2 Point decoding

Given 33 bytes `bytes`:

1. If `len(bytes) != 33`, fail.
2. Let `sign = bytes[32]`. If `sign > 1`, fail. Only `0` and `1` are valid.
3. Let `v = LE⁻¹(bytes[0..32])`. If `v >= p`, fail.
4. Compute

   ```
   u² = (1 − v²) / (a' − d'·v²) mod p
   ```

   with `a' = 479595`, `d' = 479599`. The denominator is never zero for any
   `v`: `a' − d'·v² = 0` would require `v² = a'/d' = d/a`, which is a
   non-square divided by a square, hence a non-square; but `v²` is always a
   square. The implementation still checks for zero defensively.
5. Compute `u = (u²)^((p+1)/4) mod p`. If `u²` is not a quadratic residue,
   `u²` fails the check `u·u == u²`; fail.
6. If `u == 0`:
   * if `sign == 1`, fail (the point is its own negative; there is no odd
     representative);
   * otherwise keep `u = 0`.
   Else, if `u mod 2 != sign`, set `u = −u mod p`.
7. Check `d·u² + v² = 1 + a·u²v²`. If not, fail.
8. Return `(u, v)`.

Step 7 is redundant for correctly computed square roots but is kept as a
defensive consistency check.

## 4. Keys

### 4.1 Seed expansion and pruning

A private key is a 32-byte seed. Key generation is:

```
h      = SHA-512(seed)                    # 64 bytes
scalarBytes = h[0..32]                    # 32 bytes
prefix      = h[32..64]                   # 32 bytes

scalarBytes[0]  &= 0xfc                   # clear bits 0 and 1
scalarBytes[31] &= 0x7f                   # clear bit 255
scalarBytes[31] |= 0x40                   # set  bit 254

s = LE⁻¹(scalarBytes)
A = [s]B
publicKey = enc(A)
```

The pruning follows RFC 8032 §3.2 with `c = 2` and `n = 254`:

* the bottom `c = 2` bits are cleared, so the scalar is a multiple of the
  cofactor `4`;
* the top bit (bit 255) is cleared;
* the bit immediately below it (bit 254) is set, so the scalar is in
  `[2^254, 2^255)`, which is exactly 255 bits.

The scalar is **not** reduced modulo `ℓ`. This is the RFC 8032 convention: the
scalar may be slightly larger than `ℓ`, and `[s]B` is still well defined.
Because `2^253 ≤ ℓ < 2^254`, every pruned scalar satisfies `s < 4ℓ`.

### 4.2 Public key

```
publicKey = enc([s]B)    # 33 bytes
```

The library returns `{'privateKey': seed, 'publicKey': publicKey}` from
`Ed256189.generateKeyPair`, and `Ed256189.publicKeyFromSeed(seed)` returns the
same public key. The returned private key is a copy of the seed.

### 4.3 Relationship to X256189 and XEdDSA

Ed256189 deliberately derives **independent** keys:

| Scheme | Scalar used | Base point | Public key |
|---|---|---|---|
| X256189 | `(pruned_scalar mod ℓ) · 4 mod ℓ` | Montgomery `G` (x-only) | 32-byte `x` |
| XEdDSA | `(pruned_scalar mod ℓ) · 4 mod ℓ` | Montgomery `G` | 32-byte `x` |
| Ed256189 | `pruned_scalar` (no reduction, no `·4`) | `B = Phi(G)` on `E_{d,a}` | 33-byte encoded point |

The same 32-byte seed therefore gives unrelated keys in the three schemes.
This is intentional: reusing a signing key and a Diffie-Hellman key is not a
requirement, and keeping the schemes independent avoids cross-protocol
assumptions. Protocols must not assume that `X256189.generateKeyPair(seed)`,
`XEdDSA.generateKeyPair(seed)` and `Ed256189.generateKeyPair(seed)` produce
the same key.

## 5. Signing

Input: a message `M` (arbitrary bytes) and a 32-byte seed.

### 5.1 Nonce

```
r = LE⁻¹(SHA-512(DS ‖ 0x01 ‖ prefix ‖ LE(counter, 4) ‖ M)) mod ℓ
```

where:

```
DS = "Curve256189-Ed256189-v1"    # 23 ASCII bytes
```

`counter` starts at `0` and is incremented if `r = 0`; the first non-zero `r`
is used. The 4-byte little-endian counter is a defensive retry for an
event that has negligible probability. It never changes the signature in
normal operation.

The nonce depends on the secret `prefix`, so it is unknown to an attacker, and
on the message, so it is unique per message. The signature is deterministic:
signing the same message with the same seed always produces the same 65 bytes.

### 5.2 Signature point

```
R = [r]B
Rbytes = enc(R)                   # 33 bytes
```

### 5.3 Challenge

```
k = LE⁻¹(SHA-512(DS ‖ 0x02 ‖ Rbytes ‖ publicKey ‖ M)) mod ℓ
```

`publicKey` is the 33-byte `enc(A)`. The challenge binds the signature point,
the public key, the message, the domain, and the tag `0x02`.

### 5.4 Scalar and output

```
S = (r + k·s) mod ℓ
signature = Rbytes ‖ LE(S, 32)    # 33 + 32 = 65 bytes
```

`S` is canonical (`0 ≤ S < ℓ`) by construction.

### 5.5 Where randomness enters

The signature itself is deterministic. Both secret scalar multiplications
(`A = [s]B` and `R = [r]B`) are performed with the library's optional
Montgomery-ladder blinding, which adds a random 64-bit multiple of the full
curve order `4ℓ` and uses `Random.secure()`. Blinding is value-preserving, so
it does not affect the output; it only changes the internal execution trace.
Removing the blinding would not change any test vector.

## 6. Verification

Input: a message `M`, a 65-byte signature, and a 33-byte public key.

### 6.1 Parsing

1. If `len(signature) != 65` or `len(publicKey) != 33`, return `false`.
2. Split the signature into `Rbytes = signature[0..33]` and
   `S = LE⁻¹(signature[33..65])`.
3. If `S >= ℓ`, return `false` (non-canonical scalar; rejects the
   malleable `S + ℓ` variant).
4. Decode `A = dec(publicKey)` and `R = dec(Rbytes)`. If either fails, return
   `false`.

### 6.2 Subgroup validation

Both `A` and `R` must be **non-identity points of the prime-order subgroup**:

```
A != identity,  [ℓ]A == identity
R != identity,  [ℓ]R == identity
```

This rejects the identity, the order-2 point, both order-4 points, and every
mixed-order point. It is stricter than RFC 8032, which does not require a
subgroup check when the cofactored equation is used.

### 6.3 Challenge and equation

```
k = LE⁻¹(SHA-512(DS ‖ 0x02 ‖ Rbytes ‖ publicKey ‖ M)) mod ℓ
```

Accept if and only if

```
[S]B == R + [k]A
```

as an **exact** group equation, with no multiplication by the cofactor.

### 6.4 Why the exact (non-cofactored) equation

RFC 8032 §3.4 specifies `[2^c·S]B = [2^c]R + [2^c·k]A` and notes that the
non-cofactored equation is sufficient when the inputs are in the prime-order
subgroup. Ed256189 takes the strict route:

* `S < ℓ` prevents scalar malleability;
* `R` and `A` are checked to lie in the prime-order subgroup, which removes
  low-order and mixed-order inputs;
* the exact equation then rejects sign-flipped `R` and any other variant that
  changes `R` by a non-identity element.

There is no separate cofactored verification mode.

### 6.5 Cost

| Operation | Scalar multiplications | Subgroup checks |
|---|---|---|
| Key generation | 1 (`[s]B`) | 0 |
| Sign | 2 (`[s]B`, `[r]B`), both blinded | 0 |
| Verify | 2 (`[S]B`, `[k]A`) | 2 (`[ℓ]A`, `[ℓ]R`) |

Verification deliberately spends two extra scalar multiplications on subgroup
checks. The implementation uses full-point Montgomery arithmetic with
Okeya–Sakurai `y`-recovery; there is no Edwards-only fast path yet.

## 7. Wire format

| Field | Length | Layout |
|---|---|---|
| Seed / private key | 32 bytes | opaque seed |
| Public key | 33 bytes | `LE(v, 32) ‖ parity(u)` |
| Signature | 65 bytes | `enc(R) ‖ LE(S, 32)` |
| Message | arbitrary | raw bytes; no length prefix, no prehash |
| Domain string | 23 bytes | ASCII `Curve256189-Ed256189-v1` |
| Nonce tag | 1 byte | `0x01` |
| Challenge tag | 1 byte | `0x02` |

Unlike Ed25519 (32/64 bytes) and Ed448 (57/114 bytes), Ed256189 uses 33/65
bytes. Unlike the earlier `XEdDSA` (32/64 bytes), the public key is a full
Edwards point, not an x-coordinate, and the signature contains a 33-byte `R`.

---

## 8. Domain separation

The exact preimages are:

```
nonce     = DS ‖ 0x01 ‖ prefix ‖ LE(counter, 4) ‖ M
challenge = DS ‖ 0x02 ‖ Rbytes ‖ publicKey ‖ M
```

with

```
DS = "Curve256189-Ed256189-v1"
```

The domain string and the tags are part of the hash input, not implicit
parameters. Consequently:

* an Ed256189 transcript cannot be confused with an XEdDSA transcript, even
  if the lengths were somehow made to match;
* changing the tag or the domain string changes every signature;
* a verifier that implements a different domain produces a different `k` and
  rejects the signature.

The XEdDSA domain is `Curve256189-XEdDSA-v1`; the two strings differ in the
scheme name. There is no shared `dom2` construction with Ed25519.

## 10. Edge cases and rejection rules

### 10.1 Key generation and signing

| Input | Behaviour |
|---|---|
| seed length ≠ 32 | `ArgumentError` |
| valid 32-byte seed | always succeeds; `[s]B` is never the identity because the scalar is non-zero |

### 10.2 Verification

| Condition | Result |
|---|---|
| signature length ≠ 65 | `false` |
| public key length ≠ 33 | `false` |
| `S ≥ ℓ` | `false` |
| `v ≥ p` | `false` |
| parity byte > 1 | `false` |
| `v` with no square `u²` | `false` |
| denominator `a' − d'v² = 0` | `false` |
| `u = 0` with parity 1 | `false` |
| decoded point not on `E_{d,a}` | `false` |
| `A` or `R` is the identity | `false` |
| `A` or `R` has order 2 or 4 | `false` |
| `A` or `R` has mixed order | `false` |
| `S` correct but equation fails | `false` |
| random bytes of the correct lengths | `false`, never throws |

`verify` never throws for arbitrary byte strings. It throws only if the caller
passes arguments of the wrong *Dart* type; lengths and contents are handled by
returning `false`.

### 10.3 Scalar `S = 0`

`S = 0` is structurally allowed by the parser (`0 ≤ S < ℓ`). A valid signature
with `S = 0` would require `R + [k]A = identity`; an honest signer produces
this with negligible probability. The verifier does not special-case it.

### 10.4 Non-canonical point encodings

The encoding is bijective on valid points: every point has exactly one
encoding, and every accepted byte string decodes to exactly one point. The
implementation rejects the alternatives explicitly:

* `v + p` (same residue, non-canonical bytes) is rejected by `v >= p`;
* the wrong parity of `u` is rejected by the equation or by the subgroup
  check after decoding a different point;
* a parity byte such as `0x80`, which the natural-model decoder treats as
  odd, is rejected outright because only `0` and `1` are legal.

## 11. Deviations from RFC 8032

RFC 8032 defines a family of parameters, not a single scheme. The table below
lists every place where Ed256189 chooses a value or a rule that differs from
the RFC's Ed25519/Ed448 instances or from its generic defaults.

| # | Item | RFC 8032 | Ed256189 | Reason |
|---|---|---|---|---|
| 1 | Signature curve | `E_{a,d}` with square `a`, non-square `d` | `E_{d,a}` with `a' = d`, `d' = a` | Curve256189's natural `a` is a non-square and its `d` is a square, so the natural model is not admissible. |
| 2 | Generator | Curve-specific `B` | `B = Phi(G)`, the image of the Montgomery base point | The EdDSA generator must lie on the signature curve; `Phi` maps `G` there. |
| 3 | Parameter `b` | Smallest multiple of 8 with `2^(b−1) > p` is 264 for this field | `b = 264` for the point encoding (33 bytes) | Consequence of the 256-bit field. |
| 4 | Public key length | `b` bits = 33 bytes | 33 bytes | Same as RFC's `b`-bit rule here. |
| 5 | Signature length | `2b` bits = 66 bytes | 65 bytes | `S < ℓ < 2^254`, so `S` is encoded in 32 bytes instead of 33. |
| 6 | `S` encoding | `ceil(b/8) = 33` bytes for `b = 264` | 32 bytes little-endian | `S` never needs the extra byte; keeping it at 32 makes signatures 65 bytes. |
| 7 | Hash output | `H` produces `2b` bits (528 bits for `b = 264`) | SHA-512, 512 bits | SHA-512 is the natural hash for a 256-bit curve; 512 > 2·log2(ℓ) ≈ 508. |
| 8 | Domain separation | Ed25519 PureEdDSA uses an empty `dom2`; ctx/ph variants add a context | Explicit `DS ‖ tag` for nonce and challenge; no context or prehash | Separates Ed256189 from every other scheme and from XEdDSA. |
| 9 | Nonce retry | No retry; `r = 0` is not special-cased | 4-byte little-endian counter retried until `r ≠ 0` | Defensive; the event has negligible probability. |
| 10 | Verification equation | `[2^c S]B = [2^c]R + [2^c k]A`, with the non-cofactored form allowed | Exact `[S]B = R + [k]A` | Stricter and non-malleable; valid because `A` and `R` are subgroup-checked. |
| 11 | Subgroup checks | Not required by the generic algorithm | `A` and `R` must be non-identity prime-order points | Rejects small-subgroup and mixed-order inputs instead of relying on cofactor multiplication. |
| 12 | `S` range | §3.1 writes `0 < S < L − 1`; implementations use `0 ≤ S < L` | `0 ≤ S < ℓ` | Follows the operational convention; `S = 0` is not special-cased. |
| 13 | Parity byte | Spare bit in the top bit of the final `y` byte | Separate byte, only `0` or `1` allowed | No spare bit exists in a 256-bit field element. |
| 14 | Variants | Pure, ctx, ph | Pure only in v1 | Keeps the first version small; ctx/ph can be added later under a new domain. |
| 15 | Key reuse | No requirement to match a DH key | Keys are independent of X256189/XEdDSA | Deliberate separation; see §4.3. |
| 16 | Scalar reduction | Scalar is not reduced before `[s]B` | Same (not reduced); `s < 4ℓ` | Follows RFC 8032 §3.2. |
| 17 | Secret scalar `×4` | Ed25519 clears 3 low bits so the scalar is a multiple of 8; no separate multiplication | Clears 2 low bits so the scalar is a multiple of 4; no separate multiplication | Correct adaptation of the RFC rule to cofactor 4. |

Items 3, 4 and 7 are forced by the 256-bit field; items 5 and 6 are the
chosen compact scalar encoding. Items 8–11 and 14 are deliberate protocol
choices. None of them weakens the signature equation: the accepted language
is a strict subset of what a cofactored RFC-style verifier would accept.

### 11.1 What is *not* a deviation

* The addition law is the standard twisted Edwards law of RFC 8032 §3; it is
  complete on `E_{d,a}`.
* The key derivation structure (hash the seed, split into scalar and prefix,
  prune the scalar, compute `[s]B`) is the RFC 8032 structure.
* The nonce and challenge are hashes of `prefix`/`R`/`A`/`M` reduced modulo
  the subgroup order, as in RFC 8032.
* The signature equation `S = r + k·s mod ℓ` is the RFC 8032 equation.

## 12. Security considerations

### 12.1 Strength

The subgroup order `n` is 254 bits, so the generic discrete-logarithm cost is
about `2^127` group operations. The field is 256 bits, so Pollard rho on the
subgroup is the limiting attack. This matches the intended ~128-bit security
level.

### 12.2 Deterministic nonces

The nonce is derived from a secret prefix and the message, so an attacker
cannot choose or predict it, and repeated messages do not repeat the nonce in
a way that leaks the key. The counter retry is a guard against the degenerate
`r = 0` case.

### 12.3 Malleability

Canonical `S`, exact equations, and non-identity prime-order `A`/`R` make the
signature non-malleable under the usual variants: `S + ℓ`, sign-flipped `R`,
sign-flipped `A`, low-order `R`, and mixed-order `A` are all rejected.

### 12.4 Cross-protocol separation

The domain string plus tags separate Ed256189 from XEdDSA and from any future
variant. The formats differ as well (32/64 vs 33/65 bytes). Do not feed an
Ed256189 signature to an XEdDSA verifier or vice versa.

### 12.5 Side channels

The implementation uses Dart `BigInt`, which is not guaranteed to be
constant-time. Secret scalar multiplications are blinded with a random
64-bit multiple of the full curve order, and the Montgomery ladder runs a
fixed number of iterations. These measures reduce timing leakage but are not a
formal constant-time guarantee. Deployments with strong side-channel
requirements must account for this.

### 12.6 Not audited

Ed256189 is new code in a beta release. It has not received an independent
cryptographic audit. The independent Python reference and the test vectors
reduce the risk of implementation mistakes, but they are not a security proof.

## 13. Interoperability and migration

* **Ed25519 / Ed448:** not compatible. Different curve, field, generator,
  domain, and lengths.
* **XEdDSA (this package):** not compatible. XEdDSA uses a 32-byte x-only
  public key and a 64-byte signature; Ed256189 uses 33 and 65 bytes and a
  different domain.
* **X256189:** ECDH only. Do not reuse an X256189 key as an Ed256189 key;
  the public keys and scalars are unrelated by design.
* **Batch verification:** `BatchVerify` only understands XEdDSA bundles.
  There is no batch verifier for Ed256189 in this release.

For a new protocol, prefer Ed256189 over XEdDSA. Keep XEdDSA only for
compatibility with existing data; XEdDSA is superseded and is scheduled for
removal in a future major release, not in this beta.

## 14. API

```dart
import 'dart:typed_data';
import 'package:curve256189/curve256189.dart';

final seed = Uint8List(32); // use a cryptographically secure random seed
final keys = Ed256189.generateKeyPair(seed);

final message = Uint8List.fromList('Hello!'.codeUnits);
final signature = Ed256189.sign(message, keys['privateKey']!); // 65 bytes
final ok = Ed256189.verify(message, signature, keys['publicKey']!); // true

final publicKey = Ed256189.publicKeyFromSeed(seed); // 33 bytes
final k = Ed256189.challengeFor(
  signature.sublist(0, 33),
  publicKey,
  message,
);
```

Constants:

```dart
Ed256189.seedLength        // 32
Ed256189.publicKeyLength   // 33
Ed256189.signatureLength   // 65
```

Low-level point encoding is available through `DualEdwards.encodePoint`,
`DualEdwards.decodePoint`, and `DualEdwards.isInPrimeOrderSubgroup`.
